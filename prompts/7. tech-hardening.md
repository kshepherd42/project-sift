This is a focused hardening task, not a rewrite. Do not add frontend features, real database persistence, message brokers, deployment infrastructure, or new architectural layers.

1. Inspect before changing code

Inspect:

- Domain models, contracts, and diagnostic codes.
- Document scanning and extraction.
- Batch coordination and failure isolation.
- Infrastructure storage, retention, background processing, and cleanup.
- HTTP upload and retrieval endpoints.
- Existing tests, configuration, logging, and documentation.

Identify concrete defects and missing acceptance criteria before making changes. Preserve existing contracts unless a specific defect requires a minimal justified change. Expand tests where needed to confirm future changes don't break existing behavior.

After full completion, update README to fully document backend architecture.

Do not regenerate working files or repeat reviews without a concrete reason.

2. Resource safety

Review the complete upload-to-extraction pipeline for avoidable memory consumption and uncontrolled work.

Verify and improve where necessary:

- Configurable request-size, per-file-size, file-count, and extraction limits.
- Bounded queue capacity and deterministic rejection when full.
- Bounded document and nesting complexity.
- Safe handling of deeply nested JSON, large strings, many properties, and numerous candidate documents.
- Cancellation propagation from HTTP requests through upload handling and queued processing where applicable.
- Correct ownership and disposal of streams and other disposable resources.
- Avoidance of unnecessary payload copies.
- Release of raw payload bytes after processing finishes or work is rejected.
- Thread-safe storage updates and safe application shutdown.

Use System.Text.Json for JSON validation and traversal. Do not introduce a second general-purpose JSON parser.

Set sensible configurable defaults. Reject or diagnose inputs that exceed supported limits rather than risking unbounded resource consumption.

Ensure cancellation does not leave a batch permanently Busy. Follow the existing contract for cancellation and failure diagnostics.

3. Scanner and extraction hardening

Verify:

- Full-payload scanning across binary framing and trailing noise.
- Multiple independent JSON documents.
- Top-level objects and arrays.
- Correct handling of escaped quotes, backslashes, and braces inside JSON strings.
- Deterministic, case-sensitive, per-document property-path deduplication.
- Nested object and array path notation.
- Document source offsets where supported.
- Conservative recovery only under documented, unambiguous rules.
- Separation between no-document-found outcomes and discovered documents that fail parsing.
- Failure isolation when one candidate is malformed.
- No fabricated documents or speculative extraction results.
- Structured diagnostics with stable codes.

Use targeted fixes for demonstrated defects. Do not broaden recovery rules merely to make more tests pass.

Document scanner limitations where arbitrary binary framing makes boundaries fundamentally ambiguous.

4. API and background-processing hardening

Verify:

- Upload validation and configured limits are enforced.
- 202 Accepted is returned only after successful batch registration and queue acceptance.
- Queue saturation does not leave orphaned batches marked Processing.
- Multiple uploaded files remain separate payloads.
- Invalid JSON inside a valid upload remains a document-level outcome.
- Unknown and expired batch IDs return 404 Not Found.
- Batch retrieval supports in-progress and completed states.
- Successful document results survive failures elsewhere in the batch.
- Responses do not expose raw payload bytes or JSON values.
- Unexpected failures are logged without sensitive payload contents.
- A failing batch does not terminate background processing for subsequent batches.
- Retention uses the documented timestamp and configurable duration.
- Cleanup and shutdown honor cancellation and handle recoverable failures safely.

Do not add authentication, distributed processing, retries, or unrelated infrastructure unless already required.

5. Observability

Ensure useful structured logging exists at meaningful failure boundaries.

Include relevant context where available:

Batch ID.
Payload index.
Processing duration.
Failure category.
Stable diagnostic code.

Avoid logging the same failure repeatedly at every layer. Choose the layer that owns the failure and log it there, while propagating diagnostics through the established contracts.

Never log raw payload bytes, complete JSON documents, JSON values, or potentially sensitive property values.

Do not introduce a monitoring platform or additional logging dependencies without a demonstrated need.

6. Tests

Use existing xUnit projects and conventions. Add or refine targeted tests for actual gaps.

Prioritize:

- Malformed and adversarial binary/JSON inputs.
- Deep nesting and configured resource limits.
- Invalid UTF-8 and unsupported encodings.
- Escaped string contents and ambiguous candidate boundaries.
- Incomplete JSON and conservative recovery.
- Multiple documents with partial failures.
- Queue saturation, cancellation, and worker failure isolation.
- Concurrent storage access and expiration.
- Upload size/count validation and API error behavior.
- Completed responses excluding raw payloads and JSON values.

Prefer deterministic tests with controlled timestamps and bounded waits. Avoid arbitrary long sleeps, unnecessary mocking libraries, and duplicating already comprehensive tests.

Do not assert behavior that cannot be implemented deterministically without first documenting the intended rule.
