2. Endpoints

Implement these versioned endpoints (use a v1 folder within the controllers folder).

POST /v1/batches

Accept uploaded payloads using multipart/form-data, with one uploaded file representing one payload. Support multiple uploaded files in one request.

Behavior:

- Validate the request before accepting work. (create a validator for this)
- Reject a missing file collection, an empty collection, empty files, invalid upload metadata, or exceeded configured request/file limits with 400 Bad Request, as appropriate to the existing request contract. Do this by throwing custom exceptions. We should also have a custom exception filter to convert into the appropriate response.
- Avoid reading entire files into additional buffers unnecessarily.
- Preserve each payload's identity or index through background processing and result retrieval.
- Register the batch and enqueue its work using the existing workflow.
- Return 202 Accepted with the batch ID and a URL identifying the batch resource, preferably through the standard Location header and an appropriate response body.
- Do not wait for extraction to finish before returning.
- If the queue is full or the service cannot accept work, return an appropriate 503 Service Unavailable response and ensure no orphaned batch remains marked Busy.
- Do not return 202 unless the batch has been registered and its work successfully accepted.

Malformed JSON inside an otherwise valid uploaded file is an extraction outcome, not an upload validation error. Accept the upload and let document-level results and diagnostics report the failure.

GET /v1/batches/{batchId}

Retrieve a batch by ID using the existing storage contract.

Behavior:

Return 200 OK with batch ID, status, payload/document results, extracted property paths, document types, document statuses, and structured diagnostics supported by the existing models.
Return 404 Not Found when the batch does not exist or has expired.
Support retrieving a batch while it is still Processing, using the existing model and status.
Return completed results without exposing raw payload bytes or JSON property values.
Preserve document and payload association in the response.
Do not invent document results for payloads where no JSON document was discovered.
Ensure the response representation is consistent for in-progress and completed batches.

Use appropriate response DTOs only if necessary to avoid exposing internal implementation details. Prefer the existing API-facing contracts if they already meet these requirements.

3. Upload safety and resource limits
Use configurable limits for request size, per-file size, and file count where practical.
Apply limits before unnecessary buffering or copying.
Use streaming or bounded reads where compatible with the existing Task 4 queue and worker contracts.
Ensure raw payload data is not retained after processing completes.
Never log raw uploaded bytes or potentially sensitive JSON contents.
Do not claim support for arbitrary unknown framing formats beyond the implemented extraction behavior.
Honor request cancellation while accepting and reading uploads.
Do not add authentication, rate-limiting infrastructure, or unrelated security features unless already required by the repository.

Choose sensible defaults and document the relevant configuration values. Avoid adding unnecessary abstractions or dependencies.

4. HTTP error handling and observability

Use consistent HTTP error responses and the project's existing conventions.

Invalid requests: 400 Bad Request.
Unknown or expired batches: 404 Not Found.
Queue saturation or temporary inability to accept work: 503 Service Unavailable.
Accepted asynchronous work: 202 Accepted.
Successful retrieval: 200 OK.

Use structured logging for upload rejection and unexpected API failures. Include useful context such as batch ID and payload index when available, but never log payload contents.

Do not turn document-level extraction failures into HTTP request failures after the upload has been accepted.

Do not expose stack traces or internal exception details to clients.

5. Swagger

Setup Swagger integration for api. Also create sample payloads (labeled) for various scenarios (bad request, one document, multiple, nested, etc.). But these sample payloads in the docs folder at the root level in file called sample-payloads.

6. Integration tests

Use the existing xUnit conventions and ASP.NET Core integration-testing approach already present in the repository. Reuse existing test infrastructure and dependencies where possible.

Cover at least:

Uploading one valid payload returns 202 Accepted.
Uploading multiple files creates a batch containing separate payloads.
The response contains a usable batch ID and resource URL.
Retrieving a registered batch returns 200 OK.
Retrieving an unknown batch returns 404 Not Found.
Malformed JSON is accepted as payload data and represented through extraction results.
Empty uploads and missing file collections return 400 Bad Request.
Oversized requests/files and excessive file counts are rejected.
Queue saturation returns the chosen rejection status without leaving an orphaned Busy batch.
An accepted batch eventually exposes its completed extraction results.
Mixed successful and failed documents preserve partial successes and diagnostics.
Completed responses do not expose raw payload bytes or JSON values.

Avoid flaky tests based on arbitrary sleeps. Use controlled test dependencies, bounded waits, or existing test utilities to observe background processing. Do not duplicate the extraction engine's unit tests.

If the existing hosting and background-processing design makes a particular failure mode impossible to test deterministically, document the limitation rather than introducing elaborate test-only production abstractions.

7. Verification and stopping criteria

After implementation:

Build the affected production and test projects.
Run the relevant xUnit tests once.
Fix concrete failures with targeted changes.
Report endpoints, response shapes, configuration settings, files changed, and commands actually executed.
Report unresolved issues honestly.

Do not claim builds or tests passed unless they were executed successfully.

Credit-conscious working rules

Use one Copilot Agent session without subagents. Inspect first, implement in one focused pass, verify once, and fix only concrete failures. Avoid regenerating completed work, broad refactoring, unnecessary abstractions, and duplicate contracts.
