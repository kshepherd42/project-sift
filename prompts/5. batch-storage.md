4. Infrastructure project

Create ProjectSift.Infrastructure targeting .NET 10.

Project references:

Infrastructure references Domain.
Infrastructure must not reference Application or Service.
Application references Domain only.
Service references Application, Domain, and Infrastructure as needed.
In-memory database-shaped implementation

Implement a small in-memory persistence adapter:

- InMemoryBatchDatabase owns the in-memory records and provides the minimal thread-safe operations needed by the store.
- InMemoryBatchStore implements the Domain batch-store interface and coordinates record creation, retrieval, updates, and expiration.
- Keep implementation details private to Infrastructure wherever possible.
- Use standard .NET collections and synchronization primitives; add no external persistence dependencies.
- Prevent concurrent access from corrupting records or exposing partially updated state. Use _etags to achieve this. Throw ConflictException when an error occurs due to mismatched _etags when updating.
- Avoid holding locks while extraction or other long-running work executes.
- Do not retain raw payload bytes in completed batch records.
- Do not simulate SQL queries, database connections, transaction engines, or durable storage.

The implementation is intentionally in-memory and loses all records on application restart. Its purpose is to establish a replaceable persistence boundary, not to pretend persistence is durable.

Provide an Infrastructure registration extension, such as AddProjectSiftInfrastructure, using the existing project conventions.

Register the database-shaped in-memory component and store with lifetimes appropriate for shared in-memory state.

Do not make Infrastructure responsible for hosting background workers or referencing Application.

5. Background processing in Service

Implement the background-processing workflow in the existing Service project.

- Use an in-process queue and a hosted background service.
- Accept queued batch work without requiring the caller to wait for extraction to finish.
- Register the batch before making it available for retrieval.
- Process batches using the existing coordinator.
- Update the stored batch status, results, and diagnostics when processing completes.
- Preserve partial successes and document-level failures.
- Keep batch status consistent with the existing Processing and Completed model.
- Do not mark a batch completed before its final outcome has been stored.
- Ensure an unexpected failure in one batch does not terminate the worker or prevent subsequent queued batches from being processed. Do this by whitelisting what exceptions shouldn't halt things rather than blacklisting those that should. (e.g. catch and retry with Conflict failures)
- Propagate application-shutdown cancellation appropriately.
- Log unexpected failures using structured context, including batch ID and failure category. Never log raw payload bytes or JSON values.

Use a bounded queue if appropriate to prevent unbounded memory growth. If a capacity limit is introduced, define deterministic behavior when the queue is full and ensure rejected work cannot remain indefinitely marked Busy.

Do not implement HTTP endpoints or modify frontend code.
