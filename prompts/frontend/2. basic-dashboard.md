Stage 2 — Shared UI Foundation and Dashboard

Prerequisites
The Master Implementation Instructions are in force.

Stage 1 has been completed and its report reviewed.

The existing repository conventions and API contracts are understood well enough to build the shared UI and display whatever dashboard data is genuinely available.

Objective

Establish a coherent, polished application shell and functional dashboard using the existing React/Vite architecture. Create reusable foundations for the remaining stages without overengineering.

Permitted scope

Implement shared layout, navigation, theme support, reusable presentation components, and dashboard functionality. Make only the API/service adjustments required for verified dashboard integration.

Do not implement the full upload workflow, batch-details experience, or complete history/export functionality in this stage.

Tasks
1. Establish the application shell
Reuse existing routing and styling conventions.
Implement or complete the compact left sidebar, application navigation, page header, and main content layout.
Provide clear active-navigation states and responsive behavior.
Make the dashboard and upload entry points discoverable. The upload destination may be a clearly marked placeholder or existing route until Stage 3 is complete.
Avoid dead links, misleading controls, and unnecessary navigation complexity.
2. Create shared UI patterns

Implement only the abstractions needed by multiple screens, such as:

Consistent page headings and section layouts.
Status badges with neutral handling for unknown statuses.
Loading, empty, error, and unavailable states.
Reusable buttons, inputs, accessible disclosures, dialogs, and confirmation patterns where appropriate.
Consistent formatting for timestamps, counts, and file sizes.

Follow existing component-library and design-token conventions. Avoid creating a large generic design system for a small application.

3. Implement theme support
Default to light theme.
Provide a working dark-mode toggle.
Use consistent semantic colors for surfaces, text, borders, focus indicators, and status presentation.
Ensure the theme applies to all current shared components.
Follow existing persistence conventions if present. Do not introduce storage complexity without need.
4. Implement the dashboard

Display a useful operational overview and recent activity using verified data sources.

Sort recent batches newest first where the data contract permits.
Show only metrics that can be derived reliably.
Clearly identify limited or loaded history where relevant.
Distinguish unavailable data from a genuine zero count.
Provide useful loading, empty, error, and retry states.
Include a clear upload call to action.
Ensure batch rows/cards link to batch details only when a valid batch identifier is available.

If the backend lacks history support, do not invent a history endpoint or present fixture data as live. Build the appropriate empty/unavailable experience and record the dependency for Stage 5.

5. Establish testable foundations

Add or update focused tests for navigation, theme behavior, reusable status presentation, dashboard loading/empty/error states, and data formatting as appropriate for the existing test framework.

Keep fixtures deterministic and separate from the real API service.

Verification
Run relevant existing tests and newly added tests.
Run available lint/format checks and the production build when practical.
Inspect the layout at desktop and narrow viewport sizes.
Verify keyboard navigation, visible focus, semantic structure, and light/dark contrast.
Confirm no API route or response shape was invented.
Review the diff for unrelated refactors and broken navigation.
Stop conditions

Pause affected work if dashboard integration requires an unsupported contract assumption or a backend modification. Continue independent UI work when safe.

Do not add unnecessary dependencies or replace the existing styling system simply to match a mockup.

Required report

Summarize:

Shared UI and dashboard functionality delivered.
Key files created or modified.
Design and architecture decisions.
API dependencies and limitations.
Tests and checks actually executed, with outcomes.
Accessibility and responsive checks performed.
Remaining issues and readiness for Stage 3.

Post-review updates (applied after user review)

- Improved navigation landmark accessibility consistency by naming the actual `nav` region (`aria-label="Main navigation"`) while preserving current sidebar semantics.
- Removed live health display from the Stage 2 dashboard so the UI does not imply unsupported real-time operational contracts.
- Updated the operational overview panel to an explicit unavailable state with a clear upload call-to-action.
- Hardened hash-route behavior for non-browser runtimes by guarding direct `window` access and providing deterministic fallback route state.
