Stage 3 — Upload Workflow and Batch Creation
Prerequisites
Master instructions and Stage 1 audit are available.
Stage 2 shared UI foundations are complete or their relevant conventions are established.
The actual batch-creation contract has been verified sufficiently to implement a correct request.

The multi-file transport contract is a hard prerequisite for submitting multiple files as one logical batch. If it remains unresolved, implement only safe, transport-independent selection and review behavior if appropriate, then stop before submission integration.

Objective

Implement a reliable upload workflow that supports selecting, reviewing, validating, and submitting one or more binary files as one logical batch, subject to the verified backend contract.

Permitted scope

Upload page/components, file-selection state, validation, upload API integration, submission feedback, and navigation after a confirmed successful response.

Do not implement full batch details, history, or export functionality.

Tasks
1. File selection and review
Support file-picker selection and drag-and-drop.
Support multiple selected files when consistent with the verified contract.
Show each filename and formatted file size.
Allow duplicate filenames.
Allow individual file removal and clearing the selection.
Handle empty drops, unsupported selections, duplicate selection events, and large selections gracefully.
Preserve the user's selection when validation or submission fails.
2. Contract-based validation

Apply verified file-count, per-file, aggregate-size, and other applicable limits.

Make validation errors specific and actionable.
Prevent submission while any selected file violates applicable rules.
Do not rely on filename extensions as proof that a file is a valid binary payload unless the actual contract requires that rule.
Distinguish client-side validation from backend rejection.
Avoid duplicating rules inconsistently across components.

Do not invent size limits, MIME restrictions, transport headers, or upload endpoints.

3. Submission
Require an explicit user action to submit the reviewed selection.
Use the existing API client/service layer and environment configuration.
Preserve file boundaries and required filenames/metadata exactly as the verified contract specifies.
Treat all selected files as one logical batch only if the actual backend supports that operation.
Disable duplicate submission while a request is in progress.
Show real upload progress only if the actual transport exposes it. Otherwise use an indeterminate loading indicator.
Handle timeouts, connectivity failures, validation errors, unexpected response shapes, and a successful HTTP response with a missing or invalid batch ID.

Do not navigate to batch details until the response provides a valid identifier and successful batch creation is established according to the real API contract.

4. Failure and recovery UX
Display an acknowledgment-required error dialog when submission fails.
Provide a concise summary and expandable technical details when useful.
Preserve the selected files after failure.
Allow the user to correct the selection or retry.
Prevent raw binary contents or sensitive information from being included in logs or error messages.
Handle malformed error responses without causing a secondary UI failure.
5. Successful submission

After confirmed creation, navigate to the batch details route using the actual returned batch identifier.

Ensure the route and navigation behavior align with the application's existing router. Stage 4 will complete the details experience.

Testing

Cover:

Single-file and multi-file selection.
Duplicate filenames and individual removal.
Empty selection and applicable validation boundaries.
Drag-and-drop and file picker behavior.
Submission success and request construction.
Double-submission prevention.
Upload errors and malformed responses.
Missing batch ID.
Selection preservation after failure.
Progress behavior when supported versus indeterminate loading when not supported.
Navigation only after valid successful creation.

Use mocked API responses for deterministic tests. Perform real integration verification only against an explicitly configured safe environment.

Stop conditions

Stop before implementing unsupported multi-file submission semantics. Do not invent multipart behavior, concatenation rules, or alternate endpoints.

If the backend only supports a different workflow, document the mismatch and request the minimum contract decision or authorization needed. Do not silently create multiple independent batches when the product requires one logical batch.

Required report

Report:

Upload functionality delivered.
Verified request/response contract used.
File limits and validation rules, with evidence.
Error handling and recovery behavior.
Tests and checks executed with actual outcomes.
Any unsupported backend capability or remaining limitation.
Readiness for Stage 4.
