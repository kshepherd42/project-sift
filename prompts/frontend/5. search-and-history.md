Stage 5 — History, Search, Copy, and Exports
Prerequisites
The master instructions and Stage 1 audit are available.
The actual history capabilities and their limitations are documented.
Stages 2–4 are implemented or their integration boundaries are clear.
Objective

Complete the operator's discovery and extraction workflow: find previous batches, search across extracted results and diagnostics, copy the appropriate paths, and export predictable, correctly scoped data.

Permitted scope

History UI and verified history-service integration, search/filter behavior, property-path result transformations, clipboard actions, and JSON/CSV export utilities.

Do not rewrite the upload workflow or batch-details polling lifecycle.

Tasks
1. History
Display available batches newest first.
Support search by batch ID and filename.
Support status filtering using verified backend statuses and a clear unknown-status option where needed.
Provide loading, empty, no-match, error, and retry states.
Link records with valid batch identifiers to batch details.
Preserve correct behavior when filenames are unavailable or several files share a name.
Respect verified pagination and server-side filtering capabilities.
Do not imply that a partial or paginated result set represents the complete history.

If the backend cannot support the desired history behavior, implement only what the existing contract permits and report the gap. Do not invent an endpoint or pretend client-side filtering can search records that have not been loaded.

2. Cross-context search

Implement case-insensitive substring matching across:

Property-path values.
Payload filenames.
Document names.
Diagnostic messages at batch, payload, and document levels.

A search for warehouse must match warehouse.zone.

Preserve enough context to explain why a result matched and where it came from. Ensure diagnostics remain associated with the correct hierarchy level.

Define and test the behavior for null names, missing diagnostics, empty queries, whitespace-only queries, and repeated paths.

Avoid silently changing the meaning of search based on the currently expanded tree. The search scope must be explicit and consistent.

3. Occurrences and unique paths

Maintain two distinct concepts:

Occurrences: every extracted property-path occurrence with its original payload/document context.
Unique paths: distinct path values, deduplicated according to an explicit, documented rule.

Do not deduplicate the detailed extraction results.

Where both modes are presented, clearly label the selected mode and the scope of copy/export actions. Do not lose provenance when deduplicating unless the specific output is intentionally path-only.

4. Clipboard behavior

Provide:

Copy for an individual property path.
Copy all matching property paths.
A clearly labeled action for copying all paths in the batch when applicable.

Make matching scope versus whole-batch scope unambiguous. Preserve occurrence ordering and duplicates for occurrence-based actions.

Handle unavailable clipboard APIs and permission failures with understandable feedback. Do not report success until the copy operation has succeeded.

5. JSON export

Define a stable, documented, keys-only export shape. Do not export the complete backend response.

Preserve enough batch, payload, and document context for the selected scope. Explicitly define whether the export includes every occurrence or only unique path values.

For example, a suitable shape could contain a batch identifier and a list of payload objects, each with its payload index/name and document objects containing document index/name and a propertyPaths array of strings. Treat this as a design candidate, not a mandated schema: adapt it to the actual available data and document the final shape.

Define handling for missing identifiers, nullable names, missing statuses, and empty results. Avoid silently dropping context or fabricating metadata.

6. CSV export

Produce one row per property-path occurrence.

Include these columns where applicable:

Batch ID.
Payload index.
Payload name.
Document index.
Document name.
Document status.
Property path.

Define a fixed column order and deterministic missing-value behavior.

Implement standards-compatible escaping for commas, quotes, CR/LF line breaks, and other relevant CSV-sensitive content. Quote fields consistently as appropriate, and correctly escape embedded quotes. Handle Unicode and empty strings.

Use a maintained CSV library already present in the repository if suitable; otherwise, a small, well-tested local serializer may be appropriate.

Document the chosen encoding and line-ending convention. Ensure exports use the intended scope and preserve duplicate occurrences.

7. Export usability
Provide understandable empty-result behavior.
Use safe, descriptive filenames.
Avoid unsafe interpolation into generated files.
Ensure downloads contain the intended data and correct MIME type.
Keep export transformations separate from UI components so they can be tested independently.
Testing

Test:

History sorting, search, status filters, pagination, and empty states according to actual API support.
Search matching each supported context.
Case-insensitive substring matching and nested property paths.
Null names, missing diagnostics, and repeated paths.
Occurrence preservation and unique-path deduplication.
Individual and scoped bulk-copy behavior, including clipboard failure.
JSON structure, context, empty values, and both export modes where implemented.
CSV headers, row counts, ordering, missing-value behavior, commas, quotes, newlines, Unicode, and empty results.
Filename generation, MIME type, and download content where the testing environment permits.
Stop conditions

Do not fabricate missing history data or invent a server-side search/filter API.

If the backend cannot provide the required scope of data, explain exactly which operations are limited and whether the limitation can be addressed safely in the frontend. Do not claim exhaustive search over unloaded history.

Required report

Report:

History and search functionality delivered.
Search semantics and result-scope rules.
Clipboard behavior and error recovery.
Final documented JSON and CSV schemas.
Duplicate-preservation and unique-path rules.
Tests and checks actually executed.
Remaining API limitations.
Readiness for Stage 6.
