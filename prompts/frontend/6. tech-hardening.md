Stage 6 — Project Sift Final Hardening and Engineering Handoff
Prerequisites
The Master Implementation Instructions remain in force.
Stages 1–5 are complete, or any deferred items and blockers are explicitly documented.
The repository is in a state where final integration checks can be run.
Objective

Perform a repository-wide quality review, close material defects, improve test coverage and accessibility, validate the production build, and update all relevant documentation to describe the actual delivered implementation.

This is a hardening and review stage, not an excuse for a wholesale rewrite.

Permitted scope

Bug fixes, targeted refactors, tests, accessibility and responsive improvements, API-boundary hardening, configuration validation, documentation, and justified cleanup related to Project Sift.

Do not introduce unrelated features or alter the backend contract without explicit authorization.

Tasks
1. Review the complete implementation

Inspect the current diff and relevant application code end to end.

Look for:

Duplicated or inconsistent status interpretation.
Incorrect assumptions about API fields or response shapes.
Inconsistent error handling between initial load, submission, refresh, and polling.
Unhandled nulls, empty arrays, malformed responses, and missing identifiers.
Lost results during partial failure.
Accidental deduplication of extracted occurrences.
Incorrect search scope or export context.
Memory leaks, overlapping requests, stale updates, timers that fail to clean up, and repeated polling.
Inaccessible dialogs, controls, disclosures, tables, or status announcements.
Broken responsive behavior, confusing loading states, and misleading metrics.
Dead navigation, placeholder controls presented as functional, unnecessary dependencies, and avoidable complexity.

Fix material issues within the approved scope. Explain any that cannot be fixed safely.

2. Complete the automated test suite

Use the repository's existing test framework and scripts. Extend tests for any uncovered high-risk behavior.

Verify:

Upload

Selection, removal, duplicate filenames, validation, submission, failure recovery, and multi-file contract compliance.

Batch details

Nested results, nullable names, missing fields, partial success, unknown statuses, diagnostics, and derived summary counts.

Polling

Verified terminal states, timer/request cleanup, retry bounds, manual refresh, stale-data retention, and long-running notices.

History and search

Sorting, filters, matching across all required contexts, empty states, and pagination limitations.

Copy and export

Clipboard success/failure, occurrence preservation, unique-path behavior, JSON shape, and CSV escaping.

Application quality

Theme behavior, navigation, keyboard interactions, responsive states, API configuration errors, and network failure recovery.

Keep fixture-based tests deterministic. Ensure fixtures cannot be mistaken for real production responses.

3. Validate real integration boundaries

Where an authorized local/test backend is available:

Verify batch creation using safe test files.
Verify multi-file behavior against the actual contract.
Verify retrieval and terminal-state behavior.
Verify history operations supported by the backend.
Compare representative responses and errors against the frontend's parsing and presentation.

Do not use production uploads or destructive actions. If integration tests cannot be run, report that limitation explicitly and distinguish source-based confidence from runtime verification.

4. Accessibility and responsive audit

Inspect and correct:

Semantic landmarks, heading hierarchy, labels, and accessible names.
Keyboard access to navigation, file selection, dialogs, disclosures, search, theme controls, and exports.
Visible focus and reasonable focus management.
Dialog opening, acknowledgment, and closing behavior.
Accessible status and error announcements without repetitive polling noise.
Status indicators that communicate meaning without color alone.
Table semantics, narrow-screen layouts, overflow, contrast, and reduced-motion behavior where applicable.

Use the repository's available accessibility tools if present. Do not claim a formal audit or screen-reader verification unless performed.

5. Configuration and security review
Validate required API configuration and provide a clear missing-configuration message.
Preserve environment-variable conventions.
Confirm secrets are not exposed through frontend variables or committed fixtures.
Ensure raw binary payload contents are not logged by default.
Review error messages for accidental sensitive data exposure.
Check that mock data and development-only behavior are not unintentionally used in production.
Verify no unapproved backend modifications were introduced.
6. Final verification

Inspect package scripts and execute the appropriate checks, including:

Automated unit/component/integration tests available in the repository.
Lint checks.
Formatting checks, if separately configured.
Production build.
Type checking, if configured.
Relevant end-to-end, accessibility, or integration checks that are available and safe.

Run the checks after the final code changes. Record the exact command and actual result for each.

If a command fails, determine whether it is caused by your changes, a pre-existing issue, missing tooling/configuration, or an unavailable external service. Do not hide failures or claim success based on partial output.

7. Update documentation

Review and update the README and every relevant existing developer document.

The final documentation should accurately cover:

Project purpose and user workflows.
Technology stack and major frontend architecture.
Installation and local development.
Required environment variables and API base URL configuration.
How to start the frontend and connect it to the backend.
Verified API routes and actual request/response behavior.
Multi-file upload behavior and confirmed limits.
History capabilities and limitations.
Status and polling behavior.
Search, copy, and JSON/CSV export semantics.
Testing, linting, formatting, and production build commands.
Fixture/mock usage and how it differs from real API integration.
Known limitations, unresolved backend/API gaps, and troubleshooting.
Material design and engineering trade-offs.

Remove or correct stale instructions, inaccurate endpoint descriptions, obsolete setup steps, and claims that are no longer true.

Never document an assumed contract as verified. Mark unresolved behavior explicitly. Do not include secrets or environment-specific credentials.

8. Interview-ready engineering handoff

Prepare a concise, evidence-based handoff that explains:

Delivered functionality and user workflows.
Important files and architectural boundaries.
Verified backend routes, request formats, response shapes, statuses, and limits.
Test coverage and exact checks executed.
Test, lint, format, build, and integration results.
Remaining defects, known limitations, and backend/API gaps.
Important engineering trade-offs and why they were chosen.
How the implementation handles partial success, unknown statuses, stale data, and duplicate paths.
Suggested interview talking points about reliability, accessibility, data modeling, and testing.
Stop conditions

Do not silently remove required functionality to make tests pass.

If a material issue requires a backend contract change, unavailable service, or risky unrelated refactor, document the issue and propose the minimum next step rather than exceeding scope.

Required final report

Return:

Executive summary.
Completed functionality mapped to requirements.
Key files and architectural decisions.
Verified API contracts and any unverified assumptions.
Tests executed, exact commands, and actual results.
Lint/format/type-check/build results.
Accessibility and integration verification performed.
README and other documentation updated.
Known limitations and remaining work.
Interview-relevant engineering trade-offs.
Final acceptance checklist with each item marked pass, fail, or blocked and supported by evidence.

Do not mark the project complete while concealing a failed critical check or unresolved blocker.
