Stage 1 — API Audit

Objective

Inspect the existing repository and produce an evidence-based implementation plan. Do not modify files during this stage.

Permitted scope

Read source code, configuration, documentation, tests, and available repository history. Run safe, non-mutating inspection commands and existing read-only checks where appropriate.

Do not edit application code, create files, install dependencies, change configuration, or modify the backend. Do not send test uploads to a shared or production environment. Only perform integration requests if an explicitly configured local/test environment and safe test data are available.

Investigation tasks
1. Frontend inventory

Identify:

Application entry points, routing, pages, layouts, and current functionality.
React/Vite setup, language, compiler settings, and package scripts.
Existing API client/service layer, domain types, response handling, and environment conventions.
Styling system, theme support, component library, icon system, and responsive conventions.
State-management and data-fetching patterns.
Existing test framework, fixtures, linting, formatting, and build checks.
Incomplete screens, placeholder behavior, duplicated logic, and existing defects relevant to Project Sift.

Identify what can be reused and where minimal additions are justified.

2. Backend/API contract audit

Inspect the actual backend implementation, not just documentation. Trace relevant routes through handlers/controllers, services, DTOs, validators, serialization settings, middleware, tests, and configuration.

Verify and record evidence for:

Batch creation route, HTTP method, content type, request shape, and response shape.
Multi-file transport semantics: how multiple files form one logical batch, how boundaries and filenames are preserved, and whether the existing endpoint supports the requested workflow.
Per-file, aggregate request, file-count, and other relevant size limits.
Batch retrieval route and actual history capabilities, including search, status filtering, sorting, and pagination.
Batch, payload, and document status values, including verified terminal states.
Diagnostics and property-path schemas, optional fields, nullability, and timestamp formats.
Validation failures, not-found responses, server errors, network-relevant behavior, and error response shapes.
Authentication, CORS, API base URL, timeouts, and any upload-progress constraints relevant to the frontend.

For every material conclusion, provide the source file and symbol, route, test, or configuration that supports it. Distinguish verified facts, inferred behavior, and unresolved questions.

The observed response with batch status Completed, document status Successful, and property paths shaped as { "value": "qty" } is only a known example. Do not generalize it into an exhaustive contract.

If a safe local integration environment is available, compare observed behavior against the code and tests. Do not claim live verification when only source inspection was performed.

3. Gap analysis

Compare existing functionality against the master product requirements.

Classify findings as:

Already implemented and verified.
Partially implemented.
Missing.
Broken or unsafe.
Blocked by an unresolved backend/API contract.

Pay particular attention to multi-file uploads, history completeness, unknown statuses, partial success, nullable fields, polling, search scope, duplicate-preserving exports, and connectivity recovery.

4. Proposed architecture and sequence

Propose the smallest coherent implementation plan that reuses existing conventions. Identify:

Pages, shared components, services, and data models to reuse or add.
Where API response validation and status presentation belong.
How upload, polling, search, copy, and exports should be tested.
Any justified dependency additions.
Stage dependencies and any necessary adjustments to the proposed sequence.

Do not produce frontend code or create files.

Stop conditions

If source inspection cannot establish how multiple binary files are transported in one logical batch, identify the exact missing contract and stop short of prescribing an invented request format.

Likewise, flag unsupported history operations, unknown terminal states, or missing error semantics when they materially affect the planned behavior.

Do not stop merely because a visual preference or ordinary implementation detail is undecided. Recommend a reasonable default for those cases.

Verification

Confirm that no repository files were changed. If Git status was available, report the observed status and distinguish pre-existing user changes from your own actions.

Do not claim checks were run unless they were actually executed.

Required report

Return:

Executive summary.
Frontend architecture and existing implementation inventory.
Backend/API contract table with evidence and confidence.
Multi-file upload and size-limit findings.
History, status, diagnostics, and error-handling findings.
Product requirement gap analysis.
Proposed implementation architecture and stage plan.
Commands/checks executed and actual results.
Unresolved blockers, their impact, and the minimum evidence or decision needed.
A readiness recommendation for Stage 2 and any later-stage gates.

Wait for review of the report before implementing anything.
