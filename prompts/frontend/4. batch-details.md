Stage 4 — Batch Details, Polling, Diagnostics, and Recovery
Prerequisites
The master instructions and Stage 1 contract audit have been reviewed.
The batch retrieval contract and relevant status semantics are verified.
Stage 2 shared UI patterns are available.
Stage 3's creation/navigation behavior is implemented or its integration boundary is documented.
Objective

Build the batch details experience around the real nested response structure. Make both successful extraction results and processing failures understandable without sacrificing data integrity.

Permitted scope

Batch details page, response normalization/validation, hierarchy components, diagnostics presentation, batch polling, manual refresh, and recovery states.

Do not implement the full history-search and export experience assigned to Stage 5.

Tasks
1. Validate and represent the response

Model the hierarchy:

Batch → Payload → Document → Property paths.

Use actual backend DTOs and serialization behavior as the source of truth. Validate external response data at the API boundary where appropriate.

Handle nullable document names, absent optional fields, empty arrays, missing timestamps, malformed structures, unknown statuses, and unexpected diagnostics.

Preserve the original backend status. If data is incomplete, present what can be safely represented and clearly indicate unavailable information. Do not silently discard valid child results because an optional sibling field is missing.

2. Batch summary

Display available:

Batch identifier and backend status.
Creation and completion timestamps.
Elapsed duration when meaningful timestamps are available.
Last-updated timestamp based on actual successful retrieval/refresh.
Payload, document, success, failure, and property-path counts when derivable.

Define counting rules explicitly. Do not count missing fields as zero, double-count the same document, or conflate processing completion with extraction success.

Where the backend reports completion but child outcomes are mixed, preserve the backend status and show the derived outcome separately.

3. Nested results and diagnostics
Display payloads, documents, and full property paths.
Keep all payload and document groups collapsed initially.
Show per-payload and per-document statuses.
Keep diagnostics at their correct batch, payload, or document scope.
Present concise summaries with expandable technical details.
Preserve partial successes even when siblings fail.
Use stable keys and avoid treating property-path values as unique identifiers.
Ensure null names have sensible neutral fallbacks without pretending that an index or generated label came from the backend.
4. Polling and lifecycle management

Verify terminal statuses before implementing polling.

Poll only while the batch is in a verified nonterminal state.
Avoid overlapping requests and duplicate timers.
Clean up timers and cancel obsolete requests where appropriate.
Stop polling after a verified terminal state or when the page lifecycle makes polling inappropriate.
Refresh the batch when the user returns to its details page.
Provide manual refresh.
Preserve last-known good data during transient retrieval failures.
Clearly warn when displayed data may be stale.
Use bounded retries/backoff for transient errors and provide a manual recovery action.
Avoid rapid repeated requests and infinite retry loops.
Display elapsed processing time and a configurable “Taking longer than expected” notice when warranted.

A frontend timeout is not a backend failure. Do not fabricate progress percentages, processing stages, or a terminal status.

5. Unknown statuses and partial success

Centralize status interpretation rather than scattering string comparisons across components.

Preserve the original value for display or technical inspection.
Normalize only verified equivalent variants.
Use neutral styling for unknown values.
Never treat an unknown value as success or automatically classify it as failure.
Derive partial-success summaries from reliable child outcomes and diagnostics, and label them as derived presentation.
6. Error and recovery states

Cover invalid or missing batch identifiers, not-found responses, malformed successful responses, unavailable backend, temporary polling failures, and permanently unsuccessful retrieval.

Differentiate initial load failure from refresh failure. Where existing data is available, retain it while showing a warning and a retry option.

Ensure accessible status announcements do not repeatedly interrupt the user on every poll.

Testing

Test:

Nested hierarchy and initially collapsed groups.
Null names and empty diagnostics.
Missing optional fields and malformed responses.
Success, failure, mixed-success, processing, and unknown statuses.
Summary counts and derived partial-success presentation.
Terminal-state polling shutdown.
Overlapping request prevention and cleanup.
Manual refresh, retry/backoff, stale-data recovery, and page navigation.
Long-running batch messaging without false failure.
Accessible disclosure controls and error/status announcements.

Use fake timers or the repository's equivalent only where suitable. Avoid brittle tests that depend on real elapsed time.

Stop conditions

If terminal states or required retrieval semantics remain unverified, do not guess when polling should stop. Implement independent presentation work and document the blocked behavior.

Do not modify the backend or silently reinterpret backend statuses to fit the UI.

Required report

Report:

Batch details and diagnostics functionality.
Status mapping and derived-count rules.
Polling lifecycle and recovery design.
Tests and checks executed, with outcomes.
Known response-shape or API limitations.
Any remaining lifecycle or accessibility defects.
Readiness for Stage 5.
