ProjectSift — Domain Models and Application Contracts

Objective

Establish minimal, stable Domain and Application contracts for extracting JSON property paths from documents embedded in binary payloads and processing them as batches.

Use the existing .NET 10 solution and Clean Architecture structure. Inspect the existing projects first and reuse their conventions.

1. Domain models

In ProjectSift.Domain, implement the minimal models and enums (using StringEnum converters) needed to represent:

A batch result, identified by a batch ID.
Batch status: Processing, Completed.
A payload result, identified by its payload index.
Individual document results, identified by their document index within the payload.
Document type: Object, Array, Unknown.
Document status: Successful, Recovered, Failed.
Extraction diagnostics with a stable code, human-readable message, and optional position information.

Each document result must support an ordered collection of extracted property paths and associated diagnostics.

Support payload-level diagnostics for cases where no document can be discovered.

Use immutable records or equivalent simple models where appropriate. Validate essential invariants, but avoid elaborate validation frameworks, speculative entities, and unnecessary abstractions.

2. Property-path contract

The extraction contract must support paths that preserve nesting and array structure:

EXAMPLE:

id
customer.id
items[].sku
items[].id

Deduplication is scoped to a single object type.

Preserve property-name casing. Keep ordering deterministic.

Document the chosen path escaping convention so property names containing dots, brackets, or other special characters can be represented unambiguously. Prefer a well-defined escaping scheme over ad hoc string manipulation.

Do not implement the actual JSON scanning or extraction algorithm in this task.

3. Application contracts

In ProjectSift.Application, introduce only the interfaces needed for the planned pipeline:

IDocumentExtractor: accepts a document candidate and produces a document extraction result.
IBatchProcessor: coordinates processing of a batch.
IBatchStore: stores and retrieves batch results by batch ID.

Define request/result types only where necessary to make the contracts clear.

The batch storage contract must support creating a batch in Processing status, updating its processing results, retrieving its current status, and identifying expired records or otherwise supporting the planned one-hour retention policy.

Keep interfaces asynchronous where appropriate and accept CancellationToken for operations that can involve asynchronous or long-running work, set to default CancellationToken if none is provided.

Raw payload bytes are temporary processing input. Completed records retain extraction results and diagnostics, not raw payload contents.

Do not put HTTP types, ASP.NET Core dependencies, storage implementations, background-worker logic, or JSON parsing implementation in Application or Domain.

4. Architecture rules

Enforce these project dependencies:

Domain: no project references.
Application: references Domain only.
Service: references Application and Domain.
Each test project references the production project it tests.

The storage interface belongs in Application, not Domain. The initial in-memory implementation will be added to Service in a later task.

Do not create an Infrastructure project for this task.

5. Tests

Add focused xUnit tests for actual domain invariants and model behavior, including:

Constructing valid batch, payload, and document results.
Representing successful, recovered, and failed document outcomes.
Representing object, array, and unknown document types.
Preserving separate document results when the same key path appears in both.
Representing payload-level diagnostics when no document is discovered.
Rejecting invalid identifiers or indexes only where the model contract explicitly requires it.

Do not create artificial domain behavior solely to increase test coverage. Test extraction-specific deduplication in the extraction task when the extractor is implemented.

Provide all test names planned for user review/approval before writing tests.

6. Scope restrictions

Do not implement:

JSON boundary scanning, parsing, or recovery.
The ASP.NET Core API endpoints.
Multipart upload handling.
Background processing or hosted services.
In-memory storage implementation or cleanup workers.
React/frontend changes.
Databases, message brokers, Docker, CI, or additional infrastructure.
Unnecessary repositories, domain entities, services, or packages.

Those belong to later tasks.

7. Verification

Inspect the current solution and project conventions once.
Implement only the required models, interfaces, and focused tests.
Build the solution and run the relevant xUnit tests once.
Fix only concrete failures, without unrelated refactoring.
Report changed files, architecture decisions, verification results, and any unresolved design questions concisely.

Do not claim tests passed unless they were actually executed.

Definition of done

The existing solution builds; Domain and Application contain stable contracts for batches, payloads, document results, property paths, statuses, and diagnostics; dependency direction is correct; focused tests pass; and no later pipeline tasks have been implemented.
