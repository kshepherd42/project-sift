Implement the application-level batch processing coordinator.

1. Inspect before coding

Inspect the existing repository, specifically:

Domain models, enums, document results, diagnostics, and batch-related types.
Application interfaces and contracts.
Scanner/extractor interface and implementation.
Existing xUnit tests and naming conventions.
Project references and dependency direction.

Do not regenerate or redesign existing contracts. Identify a concrete incompatibility before proposing any contract changes.

Keep dependencies compliant with the existing architecture: Application may reference Domain, but must not depend on Service.

2. Implement the batch coordinator

Implement the smallest viable application service that coordinates extraction across multiple payloads in one batch.

Requirements:

- Accept the existing batch input representation, reusing existing contracts where possible.
- Invoke the extraction engine for each payload.
- Preserve payload identity or index so results and diagnostics can be traced to their originating payload.
- Aggregate all document results and diagnostics without merging results from different documents.
- Preserve successful document results when other documents fail.
- Represent payloads with no discovered documents distinctly from payloads containing discovered but failed documents, using the existing contracts.
- Handle ordinary extraction failures at the narrowest appropriate scope so one malformed payload does not unnecessarily prevent processing the remaining payloads.
- Do not swallow cancellation, fabricate successful results, or silently discard failure diagnostics.
- Honor cancellation using the existing asynchronous conventions and CancellationToken where appropriate.
- Keep the batch outcome consistent with the existing batch status model. A batch may complete even when individual documents fail.
- Do not introduce database access, storage implementations, background execution, HTTP concerns, or frontend dependencies.

- If an unexpected exception occurs, handle it only where doing so preserves the established failure semantics and allows safe continuation. Do not catch fatal runtime exceptions indiscriminately. Preserve useful diagnostic context without exposing raw payload contents or JSON values.

3. Keep the design minimal

- Prefer one focused application service and the smallest necessary interface or contract additions but break up tasks where appropriate.

- Do not introduce generic pipelines, mediator libraries, message brokers, an Infrastructure project, speculative abstractions, or unrelated refactoring.

- If an existing Application contract already expresses the required behavior, reuse it rather than adding a duplicate abstraction.

4. Tests

Use the existing xUnit test project and conventions. Add focused tests for:

- A batch containing one payload with one successful document.
- Multiple payloads with multiple document results.
- Successful and failed documents in the same payload, preserving partial successes.
- A payload with no discovered documents.
- A failed payload followed by a successful payload, verifying failure isolation.
- Preservation of payload association and document diagnostics.
- Empty batches or empty payload collections, according to the existing contract.

Use lightweight test doubles only where needed. Avoid adding mocking dependencies if the existing test conventions do not require them.

5. Verification and stopping criteria

After implementation:

Build the affected production and test projects.
Run the relevant xUnit tests once.
Fix concrete failures with targeted changes.
Report the files changed, behavior implemented, and commands actually executed.
Identify any unresolved contract mismatch or failing test honestly.

Do not claim tests or builds passed unless they were executed successfully.
